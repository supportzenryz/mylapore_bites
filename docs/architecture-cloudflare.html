01 · why this is a real decision, not a deploy target swap

What actually moves

The VPS plan ran one Docker image twice — an HTTP process and a worker process — against a Postgres and Redis container it also owned. Cloudflare has no equivalent of "a server you SSH into": Workers are short-lived request handlers with no persistent process, so the parts of this system that assumed a long-running Node process — BullMQ polling Redis, a raw TCP connection pool to Postgres — need a different mechanism, not just a different host. The table below is the honest mapping.

02 · the shape of it

System diagram

03 · compute

Workers API — NestJS → Hono

NestJS's decorator/DI model assumes a long-lived Node process and doesn't run on the Workers runtime. Hono is the standard choice for this instead — a small router built for edge runtimes (Workers, Deno, Bun, Node), with the same shape of concerns re-expressed as plain functions and middleware rather than classes and decorators:

Maps directly

Guards → middleware (permissionsGuard(), customerAuthGuard()). Controllers → route modules. Zod contracts → unchanged, Hono validates against the same schemas. RS256 JWT verify → Web Crypto SubtleCrypto, which Workers support natively.

Needs care

Nest's request-scoped DI (one PrismaService instance injected everywhere) becomes explicit context passing — a per-request Prisma client bound to the Hyperdrive connection string, threaded through c.set()/c.get() rather than constructor injection.

04 · database

Neon Postgres via Hyperdrive

Cloudflare doesn't host a relational database itself. Hyperdrive is a connection-pooling proxy in front of a Postgres you already have somewhere else — it doesn't replace Neon, it makes talking to Neon from a Worker fast and connection-safe. This is deliberately the smallest change in the whole migration: the schema, the 61 Prisma models, every migration, the seed data, and — critically — the guarded capacity SQL are all Postgres-specific and stay exactly as written.

-- unchanged from apps/api/src/modules/capacity/capacity.repository.ts
UPDATE production_capacity
SET    "reservedUnits" = "reservedUnits" + $1, "updatedAt" = now()
WHERE  "id" = $2::uuid
  AND  "status" = 'OPEN'
  AND  "reservedUnits" + $1 <= "capacityUnits"
RETURNING ("capacityUnits" - "reservedUnits")::int AS remaining;
-- same statement, same guarantee, now reached through Hyperdrive instead of a local pool

Prisma's driver-adapter pattern (already in use for the same reason the Prisma CLI download is blocked here) is what makes this possible — swap @prisma/adapter-pg's connection string for the Hyperdrive binding, and the rest of the repository code is untouched.

05 · background jobs

BullMQ → Queues + Cron Triggers

Capacity-hold expiry sweep (every few min)→Cron Trigger
Order-confirmed → WhatsApp/SMS send→Queue consumer
Production/packing/delivery status notifications→Queue consumer
Review-request delayed send→Queue (delayed message)
Razorpay / Stripe webhook receipt→Worker route (sync ack) + Queue (follow-up)

The notification "transactional outbox" pattern is unchanged — a row is still written inside the same DB transaction as the business event; only the thing that drains that outbox moves from a BullMQ worker to a Cron-triggered sweep or a Queue consumer.

06 · state that isn't a request

Caching & rate limits — KV and Durable Objects

Workers KV

Market-by-host resolution cache (was Redis, 60s TTL) and the availability-date cache. Eventually consistent — fine for both, since both already tolerate a short staleness window.

Durable Objects

OTP attempt/resend counters and per-phone/per-IP rate limits need strong consistency (a race here is a security bug, not a UX one) — one Durable Object instance per phone number replaces the Redis INCR-with-TTL pattern.

07 · frontend

Storefront & admin on Cloudflare Pages

Next.js 15 deploys to Cloudflare Pages via the OpenNext Cloudflare adapter, which supports the App Router features already in use (server components, route handlers, image optimization). The market-resolution-by-Host middleware, the X-Market-Host forwarding to the API, and the whole component tree carry over unchanged — this is a build-target change, not a rewrite.

08 · what doesn't move

Unchanged, on purpose

  • Prisma schema — all 61 models, 21 enums, every relation and constraint
  • The capacity-reservation SQL and its concurrency proof (same statement, same guarantee, re-run against Neon before cutover)
  • RBAC model — permission rows in the DB, one guard, no scattered role checks
  • Zod contracts package — client still can't construct a request the API accepts but rejects
  • Four independent order status columns, idempotency keys, webhook exactly-once handling
  • Seed data, delivery zones, brand and storefront design
09 · action needed from you

Accounts I can't create for you

Neon (or Supabase) account

A serverless Postgres provider, for the same reason a VPS needed provisioning — I can build and test everything against a local Postgres in the meantime, but production needs a real one, and account creation isn't something I can do on your behalf.

wrangler login

Cloudflare's CLI auth opens a browser OAuth flow. Same reason the GitHub push needed you in the loop — I won't handle account credentials or tokens directly, so this step runs on your machine, once, and after that deploys are one command.

10 · rollout

Migration phases

1.5a

Compute + capacity

Scaffold the Hono app; port auth and the capacity module first — highest-risk, already fully proven. Re-run the concurrency test against the same Postgres, through the Hyperdrive-compatible driver path.

1.5b

Remaining modules

Catalogue, pricing, cart, customers, delivery, markets — same porting pattern, module by module.

1.5c

Jobs

Replace BullMQ producers/consumers with Queues and Cron Triggers per the mapping in §05.

1.5d

Frontend

Adapt storefront + admin builds to the OpenNext Cloudflare adapter; deploy to Pages.

1.5e

Cutover

Neon account created, Hyperdrive bound, DNS pointed at Pages + Workers custom domains. Docker/VPS plan retired; docs updated.

11 · read before you approve

Honest risks

Local dev changes shape

docker compose up stops being the whole story; local development moves to wrangler dev / Miniflare. Workable, but it's a different day-to-day than what's documented in the repo today.

CPU time per request is capped

Long synchronous work — the ~440-SKU CSV import, big admin reports — needs to run as a Queue consumer or a Cron-triggered batch rather than one request, not because it's slow but because Workers cap how long a single invocation may run.

Newer tooling than the VPS path

Prisma's edge/Hyperdrive driver adapters are less battle-tested than the plain pg adapter already proven in this repo. Worth re-verifying corners (raw SQL, transactions) as each module ports, not assuming parity.

More platform lock-in, not less

Queues, Durable Objects, KV and Hyperdrive are all Cloudflare-specific. Leaving the VPS plan trades "any Docker host" portability for "any Cloudflare account" portability — a reasonable trade, but worth naming.

Next step: scaffolding the Hono app and porting the auth + capacity modules starts now, developed and proven against the local Postgres exactly as before. The Neon connection swaps in the moment that account exists — nothing about the module-porting work waits on it.
