Mylapore Bites Platform Architecture

One backend, one database, one admin platform — serving mylaporebites.com and mylaporebites.co.uk as two storefronts of a single system.

The whole platform is organised around one fact: most of what you sell does not exist when the order is placed. An order is not a claim on stock — it is a reservation against a future day’s production capacity in the Mylapore kitchen. Capacity is therefore a first-class, transactional, server-owned resource, on the same footing as money. Every other module — catalogue, cart, checkout, delivery, notifications — is built around that reservation.

Deviations for your approval

D1
Worker is a second entry point of the API codebase, not a separate apps/worker project. Your sketch had apps/worker/src/ duplicating the module tree. Jobs need the same services as HTTP requests — the production engine, the pricing service, the Prisma client. Splitting them into two projects means either duplicating that code or building a third shared package and fighting circular imports. Instead: one codebase, two bootstrap files (main.ts, worker.ts), one Docker image, two containers with different commands. Identical deployment shape, none of the duplication.
D2
Domain logic lives in apps/api/src/modules/*, not in packages/production, packages/delivery etc. Packages that import Prisma and each other become a dependency graph you maintain instead of features. packages/* holds only genuinely cross-app code: Prisma client, shared types and Zod contracts, the generated API SDK, UI primitives, tooling config. If a domain module ever needs to be reused outside the API, extracting it then is a mechanical move.
D3
One storefront container serves both domains. Not two Next.js apps. Middleware resolves Host to a market and the whole app renders from that. This is what structurally prevents the two sites drifting apart — the failure mode your brief is most concerned with. Theming and copy differences are data, not forks.
D4
OTP gets an SMS fallback channel from day one. WhatsApp-only login means anyone without WhatsApp, or with a delivery failure, simply cannot log in — and you would only discover it as unexplained checkout drop-off. Same OtpChannel interface, WhatsApp primary, SMS (MSG91 or Twilio) automatic on non-delivery after ~30s. Cheap now; a rewrite of the auth flow later.
D5
Object storage is Cloudflare R2, not a MinIO container. Product images are the heaviest thing on a food site. R2 is S3-compatible, has no egress charges, and puts images on a CDN edge in Chennai and London without you running or backing up another stateful service on the VPS. The StorageProvider interface keeps MinIO available for local development.
Needs a decision from you

VPS region. Your launch market is Chennai, but Hetzner — the cheapest option — has no India region. Section 10 lays out the trade-off. I need your call before anything is provisioned.

The rule that keeps it one platform

Every request carries a market, resolved server-side from the hostname. Market is never a conditional in application code — it is a foreign key on the rows that differ.

Varies by marketMechanismNever varies
Price, currencymarket_product_variant.priceProduct identity, SKU, recipe
Tax treatmenttax_rate per market + tax classOrder lifecycle and statuses
Payment providermarket.payment_providerPayment state machine
Delivery zones, fees, slotsdelivery_zone rowsDelivery engine logic
Which products are soldmarket_product.is_activeCatalogue schema

Design guardrail

Adding the USA in 2027 should be: insert a market row, insert delivery zones, set prices, point a domain at the proxy. If it ever requires a code change, something has been modelled wrong — and that is the test to apply to every pull request.

Layering inside the API

Each domain module is controller → service → repository. Controllers validate input and nothing else; services hold business rules and own transactions; only repositories touch Prisma. Cross-cutting concerns — market resolution, permissions, rate limiting, idempotency, audit — are Nest guards and interceptors registered once, never repeated per handler.

Why contracts matters

One Zod schema per request/response shape, imported by both the NestJS validation pipe and the Next.js form. The storefront cannot construct a request the API would reject, and a breaking API change fails at compile time in the storefront rather than at runtime in a customer’s checkout.

Conventions applied throughout

  • UUIDv7 primary keys — time-sortable, safe to expose, no sequence contention.
  • Money as NUMERIC(12,2) with an explicit currency column. Never floats.
  • All timestamps timestamptz stored in UTC; business dates as DATE interpreted in the market’s timezone.
  • created_at, updated_at, and deleted_at (soft delete) on every catalogue and config table.
  • Enums as Postgres native types so the database rejects an invalid status, not just the application.
  • Indexes committed with the migration that needs them — notably (warehouse_id, variant_id, production_date) unique, (market_id, status, delivery_date) on orders, and trigram indexes on product name for search.
05

Pre-order & capacity engine

This is the section to read closely. Everything your business depends on — not promising food you cannot cook — is decided here.

What the customer experiences

Order by Thu 8:00 PM→ Prepared Fri→ Delivered Sat

None of those three dates is written anywhere in the frontend. They are computed from variant_production_rule for that exact variant, in the market’s timezone, against live remaining capacity. Change the cut-off in Admin at 3pm and the product page reflects it on the next request.

Four stock modes, one mechanism

ModeBehaviourCustomer sees
STOCKEDSold from finished inventory. No capacity reservation.“In stock · next delivery Tuesday”
FRESH_PREORDERMade to order. Reserves capacity on the production date.“Made fresh after you order” + the three dates
LIMITED_DAILYMade daily up to a cap; unsold stock carries no forward.“Only 12 left for Saturday”
PREORDER_ONLYFestival or seasonal item, explicit window.“Pre-order for Deepavali · closes 3 Nov”

Preventing overbooking

Two customers reach for the last five packs of Murukku at the same instant. The defence is not a lock held in application code — it is one statement that Postgres serialises for us:

-- Atomic reserve. Returns zero rows if capacity is gone.
UPDATE production_capacity
SET    reserved_units = reserved_units + $qty
WHERE  id = $capacity_id
  AND  status = 'OPEN'
  AND  reserved_units + $qty <= capacity_units
RETURNING capacity_units - reserved_units AS remaining;

Under READ COMMITTED, the second transaction blocks on the row until the first commits, then re-evaluates its WHERE clause against the updated row. It cannot see stale data and cannot over-reserve. Zero rows returned is not an error — it is the domain signalling “full”, and the service answers with the next available date rather than a failure.

The single most important test in the suite

Fire N concurrent checkouts against a capacity of N−1 and assert that exactly N−1 orders exist and reserved_units equals capacity_units. Run it against a real Postgres, not a mock. If that test is green, the business cannot promise food it cannot cook.

The hold is created when the customer selects a delivery date at checkout, not when they add to cart — holding capacity for browsing would strangle a small kitchen. A BullMQ delayed job releases the hold at expires_at; the release is written as a conditional update so a double-fire cannot double-decrement:

UPDATE capacity_reservation
SET status = 'RELEASED', released_at = now()
WHERE id = $id AND status = 'HELD'
RETURNING qty;   -- decrement reserved_units only if a row came back

The availability date engine

Given a cart and an address, which dates can we actually honour? Every clause below reads from configuration.

// availability/availability.service.ts — pseudocode
zone = resolveZone(address)                       // else NOT_SERVICEABLE

for each date D in [today .. today + market.orderHorizonDays]:
  if D not in zone.serviceWeekdays          → skip
  if D in blackoutDates(market, warehouse) → skip

  for each cart line L:
    rule = L.variant.productionRule
    if D not in rule.deliveryWeekdays      → reject D
    P    = previousWorkingDay(D, rule.leadTimeDays, warehouse)
    cut  = at(P - rule.cutoffOffsetDays, rule.cutoffTime, market.timezone)
    if now > cut                           → reject D
    if remainingCapacity(P, L.variant) < L.qty → reject D

  if slotsRemaining(zone, D) == 0          → reject D
  accept D
Cart-level nuance worth designing for now

A cart’s delivery dates are the intersection across its lines. Mix a shelf-stable pickle with a fresh murukku and the murukku decides. The API therefore returns, per rejected date, which line item blocked it and why — so the storefront can say “Saturday is unavailable because Murukku (500g) is fully booked” and offer to move that one item, instead of an opaque “not available”. This is the difference between a checkout that converts and one that does not.

Results are cached in Redis for 60 seconds keyed by zone and a cart fingerprint, and invalidated immediately on any capacity mutation, so the common browse case is cheap while the checkout case is always fresh.

Zone resolution order

  1. PIN code match against zone_postcode — fast, exact, and enough for a Chennai launch.
  2. Polygon containment using the saved latitude/longitude, for areas where one PIN straddles two zones.
  3. No match → a friendly “we’re not in your area yet”, and the PIN is recorded. That list is how you decide which suburb to open next.

PostGIS is not required at V1 — point-in-polygon on a stored GeoJSON works fine at Chennai scale — but the column is jsonb so migrating to PostGIS later is additive.

Fulfilment statuses

WAITING→PICKING→PACKING→QUALITY_CHECK→PACKED→ASSIGNED→OUT_FOR_DELIVERY→DELIVERED

Plus FAILED_DELIVERY and RESCHEDULED, both of which loop back to date selection and re-run the capacity check — a rescheduled fresh item may need to be made again.

Order status, payment status, production status and fulfilment status are four independent columns, not one. An order can legitimately be PAID + production COMPLETED + fulfilment PACKING. Collapsing these into a single enum is the modelling mistake that forces a rewrite six months in.

Driver app

Not in V1, as you specified. The shipment and delivery_event tables carry a nullable driver_id and accept GPS-stamped events, so a driver PWA is an additive feature rather than a schema migration.

Admin sign-in — and why role checks live in one place

Email + password (Argon2id) + mandatory TOTP MFA, separate token audience from customers, 8-hour sessions with idle timeout, optional IP allowlist for SUPER_ADMIN.

Permissions are rows of the form domain:resource:action — production:batch:update, order:refund:create. A single PermissionsGuard reads a decorator; no handler contains a role comparison:

// One guard. One decorator. Nine roles, editable in Admin without a deploy.
@Post('batches/:id/complete')
@RequirePermission('production:batch:update')
async completeBatch(@Param('id') id: string, @Body() dto: CompleteBatchDto) { … }

Roles SUPER_ADMIN, ADMIN, PRODUCT_MANAGER, PRODUCTION_MANAGER, ORDER_MANAGER, INVENTORY_MANAGER, DELIVERY_MANAGER, CUSTOMER_SUPPORT and CONTENT_MANAGER ship as seeded permission bundles, not as hard-coded identities.

Conventions

  • Cursor pagination on every list endpoint — offsets break under concurrent writes.
  • One error envelope: { code, message, details }. code is machine-readable (CAPACITY_EXHAUSTED, ADDRESS_NOT_SERVICEABLE, CUTOFF_PASSED); message is customer-safe. Stack traces never leave the server.
  • Domain errors carry a recovery hint — CAPACITY_EXHAUSTED returns nextAvailableDate, so the storefront can offer the fix, not just the failure.
  • /v1 in the path from day one, so a future native app can be pinned to a version.

Deployment, and what to do about FastHosts

The honest position on FastHosts

FastHosts shared and free hosting is built for PHP and static sites. It will not run a persistent NestJS process, PostgreSQL, Redis or background workers — and no amount of redesign would make this application fit inside it without gutting the production engine. So the split is clean:

Stays on FastHostsMoves to the VPS
Domain registration for both domainsAPI, worker, both Next.js apps
DNS zone (or delegated to Cloudflare)PostgreSQL, Redis
Business email MX, if already set up thereCaddy TLS termination

Nothing in the codebase knows FastHosts exists, so this costs nothing and locks in nothing. Before you renew anything, confirm with them that you can set arbitrary A, AAAA, CNAME and TXT records, and whether the free plan restricts changing nameservers — those two answers are the only things that matter.

Your decision: where the VPS lives

Your customers are in Chennai; the cheapest hosting is in Europe. Static and cached pages are served from a Chennai edge either way — but every add-to-cart, availability check and checkout call goes to the origin.

India origin (Linode Mumbai, DigitalOcean Bangalore, Lightsail Mumbai): roughly 20–40ms for Chennai customers, ~150ms for future UK customers, and costs more per GB of RAM.

Europe origin (Hetzner): the cheapest option by a clear margin and ideal once the UK launches, but roughly 140–180ms per API call from Chennai — noticeable on every tap.

My recommendation: India origin for launch. Chennai is the market you are actually trying to win, checkout responsiveness is conversion, and the whole stack is containers — relocating or splitting later is a data migration, not a rewrite. Revisit when UK volume justifies a second region.

Pipeline

push to main→ lint · typecheck · test→ build images → GHCR→ deploy staging→ e2e smoke→ manual approve → production

Migrations run as a one-shot prisma migrate deploy container before the new API starts, and are written to be backward-compatible for one release so a rollback never strands the database ahead of the code.

Backups and recovery

  • Nightly pg_dump -Fc, age-encrypted, pushed off-site. 30 daily plus 12 monthly retained.
  • Redis is treated as disposable — queue state is reconstructable from the database, which is why the notification outbox lives in Postgres and not only in the queue.
  • Media in R2 with versioning enabled.
  • Documented restore runbook with a target of under one hour, and a restore actually rehearsed monthly. An untested backup is a guess.

Observability

Structured JSON logs with a request ID threaded through API, worker and queue jobs; Sentry for errors in all three apps; /health and /health/ready for container orchestration; uptime monitoring on both storefronts and the API. Two business alerts that matter more than any infrastructure metric: a production plan not generated by 22:00, and a notification stuck in PENDING for over 15 minutes.
