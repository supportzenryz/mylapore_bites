01 — read this first

Three conflicts that need your decision

The BRD's category counts match this repository's seed data exactly — Podis 1, Savouries 2, Nuts & Spices 0, and so on — so it was clearly written with the current storefront in view. That makes the following three disagreements look like drift rather than deliberate reversals, which is exactly why they need confirming rather than assuming.

The business model blocking · affects everything

This is the one that matters most, because it decides what the order and inventory foundation actually is.

What's built

Orders reserve future kitchen production capacity. Nothing sits on a shelf; you pick a delivery date and the kitchen cooks for it. The guarded SQL that prevents overbooking is built and proven under concurrency.

What the BRD describes

Orders draw down warehouse stock: on-hand vs reserved vs quarantined, batch and best-before tracking, FEFO picking, goods receipt, cycle counts, pick tasks and bins.

These are different systems, not different wordings. The schema already carries a StockMode per product — STOCKED, FRESH_PREORDER, LIMITED_DAILY, PREORDER_ONLY — so both can coexist. What's undecided is which one is the centre of gravity, and therefore what gets built next and how much warehouse machinery is worth building at all.

The palette blocking · contradicts a recent instruction

The BRD's D-03 is marked "Accepted direction", but its maroon is the colour you specifically asked to remove ("white BG and no kukum color"), and the storefront was retoned to the eatdesi.uk palette two days ago at your request.

The launch market blocking · changes payments, tax, copy

BRD

United Kingdom first. GBP. Stripe as candidate. UK VAT, distance-selling and food-labelling advisers.

What's built

India first. INR, Asia/Kolkata, four real Chennai delivery zones with live PIN codes, Razorpay. The UK market row exists and is seeded but inactive.

The multi-market architecture handles either — market is a database row, never a branch in code — so this is a sequencing decision, not a rebuild. But it changes which payment provider gets wired first, which tax rules get modelled, and whether delivery zones are Chennai PIN codes or UK postcodes.

Honest summary: one P0 fully built, four partial, four not started. What exists is the foundation — catalogue, cart, auth, permissions, the capacity engine and the storefront. What does not exist is the commercial spine: checkout → payment → order → fulfilment. That is the next body of work, and it is the bulk of the BRD.

03 — worth knowing

Things the audit turned up

  • Guest checkout needs a schema change. Order.customerId is currently required, so an order cannot exist without a registered customer. BR-003 is P0, so this migration comes first in the checkout slice.
  • The overselling proof covers half of BR-007. It is genuinely proven — 30 concurrent checkouts against capacity for 29 yield exactly 29, never more — but it protects kitchen capacity. A product marked STOCKED has no equivalent atomic guard yet.
  • Authentication doesn't match the BRD's API sketch. The BRD lists /auth/register, /auth/login, /auth/forgot-password — password-based. What's built is phone + WhatsApp OTP with SMS fallback, and no customer password at all. Not a conflict worth blocking on, but the BRD's endpoint list won't match reality unless email/password is added alongside.
  • Permissions are kitchen-shaped, not warehouse-shaped. There are production:capacity, production:batch, production:plan and packing:order permissions, but no pick-task, stocktake or cycle-count permissions, and no Finance role with refund limits.
  • Several BRD entities already exist as models with no code behind them. Order, OrderItem, Payment, Refund, Shipment, Coupon, PromotionRule, InventoryItem, AuditLog, IdempotencyKey. The migration cost of the next phases is lower than the BRD implies.
  • Prisma tooling is still blocked in this sandbox. binaries.prisma.sh returns 403, so prisma generate and migrate cannot run here. They work on any normal network — your machine included — but it means migrations are authored here and run on your side.
04 — not in the BRD

Built work the BRD doesn't mention

Listed so nothing gets quietly discarded if the BRD is treated as the sole source of truth:

  • The production capacity engine — cut-off times, production weekdays, lead times, per-day capacity, "next available date" answers instead of bare refusals.
  • WhatsApp OTP authentication with SMS fallback, Argon2id-hashed codes, rotating refresh tokens with reuse detection.
  • Delivery zones and slots — polygon and PIN-code matching, per-zone fees and minimums, slot capacity allocation.
  • Multi-market architecture — .com and .co.uk from one backend, market resolved from the request host, market-scoped pricing.
  • The Cloudflare migration, one module in. Note the BRD's architecture table proposes NestJS + Redis + BullMQ on AWS or a VPS, which describes the pre-migration stack.
